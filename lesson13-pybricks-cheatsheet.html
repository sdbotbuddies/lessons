Getting set up

Every program starts by saying what's plugged in where.

from pybricks.hubs import PrimeHubThe brain
from pybricks.pupdevices import Motor, ColorSensor, UltrasonicSensor, ForceSensorThings you plug in — only import the ones you use
from pybricks.robotics import DriveBaseTwo wheels as one robot
from pybricks.parameters import Port, Direction, Color, Stop, Button, IconThe named values you pass in
from pybricks.tools import wait, StopWatchWaiting and timing
hub = PrimeHub()Wake up the hub
arm = Motor(Port.C)A motor in port C
Motor(Port.A, Direction.COUNTERCLOCKWISE)A motor mounted backwards — use this when a wheel spins the wrong way

Two kinds of name on this sheet.
Motor Port Color — Capital letters means it's Pybricks' name. Spell it exactly.
hub arm robot — lowercase means it's a name you chose when you made the thing. Call yours whatever makes sense — claw, lifter, left_wheel.

Driving — DriveBase

robot = DriveBase(left, right, wheel_diameter=56, axle_track=112)

robot.straight(300)Forward 300 mm. Negative = backwards
robot.turn(90)Spin in place 90 deg. Negative = left
robot.arc(200, angle=90)Curve along a circle of radius 200 mm. + curves right, − curves left. Give angle OR distance, not both
robot.move_by(400, 200)Go to a point 400 forward, 200 left mm. Turns then drives. Uses the field direction, not the way you're facing
robot.drive(100, 0)Keep driving at 100 mm/s, turning at 0 deg/s. Doesn't stop on its own
robot.stop()Stop driving
robot.use_gyro(True)Measure real angles instead of counting wheel turns
robot.distance() robot.angle()How far / how much you've turned since reset()
robot.settings(200, 400, 150, 300)Speed, then how quickly it speeds up — driving, then turning

Motors — for arms and attachments

arm.run_angle(500, 180)Turn 180 deg from here, at 500 deg/s
arm.run_target(500, 90)Turn to the 90 deg position
arm.run_time(500, 2000)Run for 2000 ms
arm.run(500)Just keep going until told otherwise
arm.angle()Where is it now? deg
arm.reset_angle(0)Call this position zero from now on
arm.stop()Let it go loose
arm.brake()Slow it down gently
arm.hold()Freeze it exactly here, actively

run_angle vs run_target: angle means "from wherever you are" — target means "to this exact spot". Target is the one you want for an arm with real positions.

Stall detection — "it can't move any further"

A motor is stalled when it's pushing but nothing is moving. That's not always a bug — sometimes it's how you find out where something is.

arm.run_until_stalled(-200, then=Stop.HOLD, duty_limit=30)A motor only. Runs until it physically can't. Gives back the angle where it stopped.
duty_limit=30Use at most 30% power — nudge the mechanism instead of grinding the gears. Applies to that one motor, for that one command only
arm.stalled()Yes or no — is this motor stuck right now?
robot.stalled()Yes or no — is the drive base stuck right now?

⚠️ The drive base has no run_until_stalled. Only a single motor does. For a drive base you drive and watch:
robot.drive(50, 0) · while not robot.stalled(): wait(10) · robot.stop()

Two things teams actually use this for:
1. Finding a true zero. Run the arm gently down until it stalls at the bottom, then reset_angle(0). Now every position is the same every run.
2. Squaring up on a wall. Drive slowly into a wall and watch for robot.stalled() — the robot straightens itself against it. A free reset, no sensors needed.

The hub — screen, buttons, light, sound

hub.display.icon(Icon.HEART)Show a picture
hub.display.number(3)Show a number
hub.display.text("GO")Scroll some text
hub.display.off()Blank the screen
hub.buttons.pressed()Which buttons are down right now — use if Button.CENTER in …
hub.light.on(Color.RED)Light around the button
hub.speaker.beep()Beep. Or beep(frequency=800, duration=200)
hub.system.set_stop_button(Button.BLUETOOTH)Pick a panic button that stops everything

The hub's own senses

hub.imu.tilt()Two numbers: pitch and roll deg — how tipped over it is
hub.imu.heading()Which way it's facing deg
hub.imu.reset_heading(0)Call this direction zero — do this before a run so old mistakes don't carry over
hub.battery.voltage()Battery level mV — under about 7600 and the robot drives short

Sensors you plug in

Make it first, then ask it questions. The name on the left of the = is yours to choose.

color_sensor = ColorSensor(Port.E)Colour sensor — looks at a surface
color_sensor.reflection()How bright the surface is, 0–100. Black ≈ low, white ≈ high
color_sensor.color()What colour it sees — compare with Color.RED etc.
color_sensor.ambient()How bright the room is, 0–100
distance_sensor = UltrasonicSensor(Port.D)Ultrasonic sensor — the one with eyes
distance_sensor.distance()How far to the nearest thing mm
distance_sensor.presence()Is another ultrasonic sensor nearby?
force_sensor = ForceSensor(Port.F)Force sensor — the press-me one
force_sensor.force()How hard it's being pressed N
force_sensor.pressed()Is it being pressed at all?

⚠️ force_sensor.pressed() is about the sensor you plug in. hub.buttons.pressed() is about the buttons on top of the hub. Different things, similar names.

Waiting and timing

wait(1000)Do nothing for 1000 ms
timer = StopWatch()Start a stopwatch
timer.time()How long since it started ms
timer.reset()Back to zero
timer.pause() timer.resume()Stop and restart the clock

Seeing what your robot is doing

You can't fix what you can't see. How you look depends on whether the laptop is still connected.

print("distance", robot.distance())While connected: shows up in the VS Code terminal as the program runs. Always print a label, never a bare number
hub.display.number(7)Not connected: put a number on the hub and watch it while the robot drives
hub.light.on(Color.RED)Colour-code where you are: green = driving, orange = arm, red = something's wrong
hub.speaker.beep()A checkpoint you can hear — you don't have to look away from the robot
timer = StopWatch() … timer.time()How many ms did that part take? Find your slow mission

🔌 Yes, this works while the robot is driving. Bluetooth stays connected for the whole run, so lines appear in the terminal live. Just don't walk out of range.

📋 To collect a lot of numbers: put them in a list while the robot runs, then print the whole list at the end. Printing inside a fast loop slows the loop down — which changes the very thing you were trying to measure.

⚠️ DataLog does not work on SPIKE Prime. Python will let you import it, so it looks like it should — but it only saves files on the older EV3 brick. Use the trick below instead.

Saving numbers to a spreadsheet 📊

There's a hidden feature: print a line starting PB_OF: and everything after it gets saved to a file on your laptop instead of the terminal — until you print PB_EOF. The file lands next to the program you ran.

print("PB_OF:tuning.csv")Start saving. Creates tuning.csv beside your program
print("time,distance")Your column titles — commas between them
print(t, ",", d)One row of numbers. Repeat as the robot runs
print("PB_EOF")Stop saving. Prints go back to the terminal

Then double-click the .csv — it opens in Excel or Google Sheets, and you can draw a graph of what your robot actually did. This is the best way to tune a line follower: log the reflection reading and the correction, then look at the shape of the wobble.

⚠️ This isn't in the official documentation. We found it by reading the source code of the upload tool. It works today — but if it ever stops, that's why, and plain print() will still be fine.

Tips for tuning a mission

Change one thingChange two and you won't know which one helped
Run it three timesSame code, same start. If the results differ, your problem is repeatability — not the number you were adjusting
Write down the batteryNote hub.battery.voltage() next to your results. Numbers tuned on a full battery won't hold on an empty one
Mark your startTape the mat so the robot begins in exactly the same spot. Otherwise you're tuning the placement, not the code
Test the piece, not the runWrite a tiny program that only does the bit you're fixing. Don't drive the whole mission to test the last 10 cm
Guess firstSay what you think will happen before you run it. When you're wrong, you've learned something — that's the whole point

Animations — these keep going by themselves

Start one and your program carries straight on. It repeats until you change it. Handy for showing "I'm working" during a mission.

hub.display.animate([Icon.HAPPY, Icon.SAD], 300)Cycle pictures, 300 ms each
hub.light.animate([Color.RED, Color.BLUE], 200)Cycle light colours
hub.light.blink(Color.GREEN, [200, 400])On 200 ms, off 400 ms, forever

⚠️ Mistakes everybody makes

Robot drives way too farYou thought in centimetres. straight(30) is 3 cm, not 30
Turns are wrongMeasure axle_track — wheel centre to wheel centre. And turn the gyro on
Distances are slightly offMeasure wheel_diameter across the middle of the wheel
One wheel goes backwardsSwap Direction.CLOCKWISE on that motor
It worked yesterdayCheck the battery before anything else
drive() never stopsIt's not supposed to. You have to call stop()

🚀 When you're ready — two things at once

Normally one line finishes before the next starts. Sometimes you want the robot to drive while the arm lifts — that's multitasking, and it needs two new words: async and await.

from pybricks.tools import multitask, run_taskBring them in
async def lift(): await arm.run_angle(500, 180)A job that can pause and let others run
await multitask(drive(), lift())Do them together, wait for both
run_task(main())The one line that starts it all

Don't start here. Get missions working one step at a time first, then come back when you want to save seconds.
